# 架构 — CV-Align | Multi-Agent Resume Screener

## 问题

给定一份或多份简历（PDF）和一份职位描述（JD），产出一份排序后的候选名单，其中每位候选人的分数都是**可解释的**：哪些板块匹配、哪些证据支撑了分数、还存在哪些差距，以及候选人可以如何改进。

早期的单次（single-pass）设计只返回一个数字，推理过程无从追溯。本版本将工作拆分为多个专职智能体，使每个阶段都可以独立检查、独立测试、独立改进。

## 函数 vs. 智能体

当任务是确定性的，我们使用普通的 Python **函数**；只有当任务需要判断力时，才使用**智能体**（即 LLM 调用）。这样既能压低成本，又能在尽可能多的环节保证行为可复现。

| 任务 | 实现方式 |
|------|----------------|
| PDF → 文本 | 函数（`pypdf`） |
| 文本 → 结构化简历 | 智能体 |
| JD 文本 → 结构化要求 | 智能体 |
| 简历分块 + 证据检索 | 函数（分块是确定性的；通过 Gemini embeddings API 按嵌入相似度对分块排序——并非 LLM 推理调用） |
| 简历 ↔ JD 板块匹配 | 智能体（现已基于检索到的证据） |
| 子分 → 最终分数 | 函数（加权和） |
| 客观的简历质量检查（卫生检查） | 函数（基于规则） |
| 差距 / 建议 / 结论 | 智能体 |

## 证据检索（RAG 层）

**动机。** 在这一层出现之前，匹配器是把*整份*结构化简历当作一整块 JSON 通读后为每个板块打分的。打分之前并没有一个明确的步骤告诉它"这里是与这条 JD 要求最相关的简历证据"——匹配器只能自己在其余信息的包围中把它们找出来。检索器把这一步显式化：在匹配器运行*之前*，先找出每个板块最匹配的简历摘录，使打分建立在检索到的证据之上，而不是靠匹配器自己在整份文档里盲目搜寻。

**分块。** `pipeline/retrieval.py::build_chunks` 把 `StructuredResume` 拆分为每个有意义条目一个分块：每段工作经历一个、每个项目一个、每条教育经历一个，另外整份（扁平的）技能列表单独作为一个分块。完全为空的条目会被跳过。每个分块携带 `section`、一个用于展示的可选 `title`（公司/职位、项目名、院校），以及重建出的 `text`。这一粒度避免了两个极端——每个板块一个分块（太粗，无法区分具体哪个项目/职位相关）和每句话一个分块（任意切出的碎片，缺乏独立含义）。

**嵌入。** 检索层通过 `langchain-google-genai` 使用 Gemini 的 `gemini-embedding-001` 模型为分块文本和由 JD 派生的查询生成嵌入——该包本来就是必需依赖（用于 Gemini 聊天模型选项），因此这**没有新增任何包**。这使得检索是真正的*语义*检索（这正是目标），而不是关键词/哈希匹配。代价是：即便 `LLM_PROVIDER=groq`（按 `.env.example`，这是本仓库的实际默认值），检索层也会依赖 `GOOGLE_API_KEY`——Groq 没有嵌入 API，因此除非依赖某个嵌入服务提供商，否则无法保持检索的语义性；鉴于项目已有 Gemini 集成，Gemini 的免费额度是务实之选。大多数旧教程引用的 `text-embedding-004` 模型已被 Google 于 2026-01-14 弃用并停服；`gemini-embedding-001` 是当前稳定、正式发布（GA）且支持免费额度的替代模型（在构建该功能时已对照 Google 官方文档核实，并非凭空假设）。模型可通过 `EMBEDDING_MODEL` 设置覆盖。

**向量库。** 并没有持久化的向量库。分块嵌入是在检索节点内、针对单份简历的一次筛选运行而计算的，只保存在局部变量中——从不写入 `PipelineState`，从不持久化，也不会作为长期索引加载。这契合部署目标（内存受限的 Hugging Face Space）：任何与嵌入相关的内容都不会在内存中存留超过单个请求。

**检索。** 对于四个板块中的每一个，`retrieve_evidence` 都会根据相关的 `StructuredJD` 字段构建一个查询（技能来自 `required_skills`/`nice_to_have_skills`；经验来自 `responsibilities`/`title`/`min_experience_years`；项目来自 `responsibilities`/`required_skills`；教育来自 `qualifications`），为其生成嵌入，并按余弦相似度对该板块自己的分块排序。所有分块文本这一批、所有板块查询这一批，各自只需一次 API 调用即可完成嵌入（而不是每个分块/查询各调一次），因此一份典型简历大约只需两次嵌入请求，而不是几十次。低于 `min_similarity`（0.80）的结果会被直接丢弃，而不是用不相关的 top-k 分块凑数——没有真正相关证据的板块会返回空列表。匹配器的系统提示词明确区分"未检索到证据"与"候选人不具备该技能"，并指示它绝不编造简历中不存在的证据。

在用真实的 Gemini 嵌入器对黄金数据集（golden dataset）的一批查询运行测试（`scripts/inspect_similarity.py`）之后，`min_similarity` 从最初猜测的 0.3 重新校准为 0.80：稠密嵌入会把较短的简历/JD 文本压缩到比离线词法假嵌入器窄得多、整体偏高的相似度区间内，因此针对假嵌入器调出的阈值对真实 API 毫无区分度——每个负例对照查询都检索到了本不该有的证据。实测中，同领域匹配在技能/经验/项目上的得分介于 0.850-0.914，而每一对跨领域组合（包括仅共享一个重叠技能的组合）最高只有 0.789；0.80 正好落在两者之间的空隙里。这只是一个小规模的经验样本，并非经过验证的最优常数——如果生产使用中发现匹配器频繁对本应匹配的内容得到"未检索到证据"，就值得重新审视。由于两种嵌入器的分数分布不可比，离线测试会显式传入自己的低阈值（`tests/test_retrieval.py::_FAKE_MIN_SIMILARITY`），而不是继承这个面向生产调校的默认值。

用真实阈值对 65 条查询的黄金数据集完整跑一遍的结果是 **Recall@4 = 0.89**（58/65），且 **14/14 个负例对照一无所获**——所有未命中都集中在 `education` 板块，技能/经验/项目则从未失手（各 100%）。用 `inspect_similarity.py` 排查后找到了原因：一个真实的教育匹配（例如用 "B.Tech Computer Science" 去匹配要求 "Bachelor's degree in Computer Science" 的 JD）得分为 0.784——*落在*别处测得的跨领域假阳性（0.759-0.789）同一区间内，并没有明显高于它。这是一个有意为之、经过理解的权衡，而不是需要继续追查的 bug：把阈值降到足以捕获那个教育匹配，很可能在其他板块重新引入假阳性，因为分数区间是重叠的。况且教育在 `DEFAULT_WEIGHTS` 中权重最低（0.10），而且无论检索结果如何，匹配器始终能看到完整的结构化简历，所以漏掉教育证据的高亮并不会夺走匹配器本可利用的信息——只是意味着该板块的分数没有建立在检索证据之上。在这个缺失代价最低的板块上，我们选择了精确率（零伪造的跨领域证据）而非召回率。

**证据注入。** `retrieve_evidence_node`（位于 `pipeline/graph.py`）在每份简历上运行一次，时机介于 `parse_jd` 与 `match` 之间，把分块和检索到的证据存入 `PipelineState`。`match_node` 将 `state.retrieved_evidence` 传入 `agents/matcher.py::match()`，后者在提示词中附加一个 `## RETRIEVED EVIDENCE` 块（每个板块：分数、标题、引用文本，或一行明确的"未检索到证据"）——这是在它本已收到的完整结构化简历之外**追加**，而非替代，因此不丢失任何既有行为。

**自修正。** 评审器 → 匹配器的重试边（`prepare_retry → match`）在图拓扑上完全绕开了 `retrieve_evidence`，因此重试会复用同一批检索到的证据（且不会重新生成任何嵌入）——匹配器只是在同一批有据可依的证据上再推理一次，外加评审器的反馈。

**测试。** 除嵌入调用本身之外，上述一切都是纯粹、确定性的 Python。嵌入调用被隔离在 `embeddings/client.py::get_embedder()` 之后（与 `llm/client.py` 的提供商工厂如出一辙），并在所有本就注入聊天模型的地方作为参数一并注入（`build_pipeline`、`run_pipeline`、`screen`，以及 `/screen` 的 FastAPI 依赖项）。离线测试注入一个小型、确定性的哈希/词袋假嵌入器来代替调用 Gemini——足以验证排序逻辑，且从不在生产中使用。整个测试套件中没有任何测试需要 `GOOGLE_API_KEY` 或网络访问。

## 编排与角色

更高一层（`pipeline/screen.py`）用同一套引擎服务两种角色：

- **candidate（候选人）** — 一份简历，获得完整的评审反馈以改进简历。
- **recruiter（招聘者）** — 多份简历针对一份 JD 排序。在 `full` 评审模式下，每位候选人都会被评审；在 `fast` 模式下，先给所有简历打分，只对 **top-K** 进行评审，在大规模场景下节省 LLM 调用。

JD 只解析一次并在所有简历间复用（解析节点是幂等的），简历则通过 `asyncio` 并发处理。`enable_critic` 标志驱动卫生检查节点之后的一条条件边，使 fast 模式可以跳过内联评审，只评审排名前 K 的候选人。

## 持久化

每次筛选运行由 `storage/runs.py`（标准库 `sqlite3`，无额外依赖）存储为一行包含完整 JSON 结果的记录，可通过 `GET /runs/{id}` 取回、通过 `GET /runs` 列出。每次操作都会新建连接，使该存储可以安全地从 FastAPI 的工作线程中调用。

## 设计决策

- **按简历划分的流水线，并行执行。** 每份简历独立运行完整流水线（`asyncio.gather`），最后一轮统一排序。这样易于调试、便于重试，也避免了把多份简历塞进一次调用所带来的长上下文近因偏差。
- **匹配器返回子分 + 证据，而非最终数字。** 每个板块（技能、经验、项目、教育）独立打分，附引用证据和简短理由。
- **评分器是确定性的。** `final = Σ weightᵢ · sub_scoreᵢ`。权重为硬编码默认值，可选地按请求覆盖。数学可证明、可调参，且无需改动提示词。
- **评审器驱动单一自修正循环。** 如果评审器对打分的置信度低，它会设置 `needs_rescore`，图随之回跳到匹配器一次（`retry_count < max_retries`）。仅这一条条件边，就足以成为用 LangGraph 而非普通函数调用的理由。
- **可配置的评审器。** `fast` 模式只对排名前 K 的简历运行评审器；`full` 模式对每份简历都运行。
- **可配置的检索。** `retrieval_top_k`（默认 4，可按请求设置）限制每个板块向匹配器呈现的证据分块数量，与 `critic_top_k` 呼应。

## 共享状态

所有节点都读写同一个 `PipelineState`（Pydantic）。它随着智能体运行不断累积结构化输出，跟踪重试记录，并维护一个 `trace` 列表——每次智能体调用记一条——最终成为持久化到 SQLite 的可解释性/审计日志。

具体定义参见 `src/multi_agent_resume_screener/state.py`（在 Step 4 中加入）。
